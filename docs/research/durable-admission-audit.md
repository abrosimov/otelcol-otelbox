# Research: Durable OTLP admission audit

## Objective

The audit asks whether this contract holds for the edge and gateway roles,
separately for traces, metrics and logs:

> When an OTLP request receives a successful response, every accepted item has
> crossed a durable admission boundary on every required delivery path and can
> survive an immediate crash and restart, under stated storage and failure
> assumptions: `ACK(e) ⇒ Durable(e, r)` for every `r ∈ R(e)`.

The answer must also separate durable admission from eventual delivery, and
state what a future Go telemetry producer may rely on.

The problem framing follows the FPF Library: one C.22.2 ProblemCard per claim,
in [problem-cards/](problem-cards/). The faults and their tests are in
[the failure matrix](durable-admission-failure-matrix.md). This note gives the
joint result and does not repeat the cards' evidence tables.

Each claim below carries one of four evidence grades: **proven by test**,
**supported by inspected source**, **assumed from external contract**, or
**not yet proven**.

### Finding 02: the acknowledgement path

The producer's response is written by the OTLP receiver after `Export`
returns. `Export` calls the pipeline synchronously. A gateway trace request
passes through the fan-out consumer, which calls every pipeline in turn and
joins their errors. Each pipeline's processors tail-call the next consumer.
The pipeline ends in `exporterhelper` `QueueBatch.Send` and then
`persistentQueue.Offer`. `Offer` returns after one storage `Batch`, which
writes the item and the advanced write index in a single bbolt transaction.
That transaction calls `fdatasync` on the data pages and then on the meta page
before it returns. No processor, wrapper or exporter layer on this path holds
data in memory before the queue. Batching happens on the consumer side of the
queue.

- **Grade:** supported by inspected source. References are in
  [PC-01](problem-cards/PC-01-ack-after-persistent-enqueue.md) and
  [PC-02](problem-cards/PC-02-storage-commit-and-fsync-boundary.md).
- **Durable admission boundary:** the return of the committed bbolt
  transaction for every required exporter's queue. A producer receives success
  only after that.

### Finding 03: guarantees by role, signal and protocol

`ACK ⇒ Durable` after SIGKILL:

| Role | Logs | Metrics | Traces | Protocols |
| --- | --- | --- | --- | --- |
| Edge | proven by test | proven by test | proven by test | HTTP and gRPC |
| Gateway, all-signal recipient | proven by test | proven by test | proven by test | HTTP and gRPC |
| Gateway, selected-traces recipient | n/a | n/a | proven by test | HTTP |
| Gateway, mixed request across both trace recipients | n/a | n/a | proven by test (no acknowledgement while either branch cannot enqueue) | HTTP |

Concurrent admission from several producers into one WAL loses or overwrites
nothing (proven by test). For a gateway trace request the required recipient
set `R(e)` is decided per resource by `filter/selected_traces`. A resource that
the filter drops makes its branch return success; that is an intentional
discard, not a loss (supported by inspected source,
[PC-03](problem-cards/PC-03-gateway-trace-fan-out.md)).

### Finding 04: the safety property and its assumptions

The safety property is:

> Acknowledged(e) ∧ restarted ∧ durable storage preserved ⇒ e recoverable or
> already delivered.

It holds under these assumptions:

1. The storage device honours `fdatasync` on Linux and `F_FULLFSYNC` on macOS
   (assumed from external contract).
2. Compaction and the data share one filesystem, as both profiles configure
   them (supported by inspected source).
3. No power loss occurs within the window after a compaction rename, because
   the directory is not synchronised (supported by inspected source;
   [PC-06](problem-cards/PC-06-compaction-crash-safety.md)).
4. Exporter IDs and storage directories do not change across restarts. A
   renamed exporter orphans its WAL without warning (supported by inspected
   source).

Two upstream hazards remain **not yet proven** and can violate safety inside
their windows:

- A storage write that fails while an item is being dispatched deletes the
  item ([PC-13](problem-cards/PC-13-read-side-storage-failure-drops-acknowledged-item.md)).
  The drain path at `max_size` was tested and loses nothing. The contended
  path, with new admissions arriving at the limit, is not refuted.
- A second crash during the restart re-enqueue of in-flight items loses them
  ([PC-14](problem-cards/PC-14-restart-re-enqueue-window.md)).

### Finding 05: capacity and backpressure

| Condition | Producer sees | Grade |
| --- | --- | --- |
| Queue full | The request blocks until its deadline, then gets an error; never a 200 | proven by test |
| Queue full on one recipient | Ingest stays blocked while that queue is full. The other signals' queues stay independent | proven by test |
| Storage at `max_size` | HTTP 503 "the storage extension has run out of available space"; earlier acknowledgements are delivered after the limit clears | proven by test |
| Real ENOSPC | bbolt rolls back the commit and the producer gets an error | supported by inspected source |
| `memory_limiter` refusal | 503 / `Unavailable` without `Retry-After`, not 429 | supported by inspected source |
| Request larger than `queue_size` | Blocks until the deadline, on every retry | supported by inspected source |

Temporary unavailability shows up as backpressure. Permanent inability to make
progress shows up the same way and is indistinguishable from the outside.
Examples are an undeliverable recipient with infinite retry, or a request
larger than the queue. Telling them apart needs telemetry
([PC-04](problem-cards/PC-04-capacity-early-warning.md)):

- Queue fill is measurable through `otelcol_exporter_queue_size` and
  `otelcol_exporter_queue_capacity`. Under the bytes sizer they report bytes,
  although they declare the unit `{batch}`.
- `file_storage` exports no metrics.
- On macOS, no role measures free disk.
- The edge's own self-metrics travel through the queue they describe.

Two further facts about the queue and storage limits:

- After a failed write the queue does not roll back its size counters, so free
  capacity is understated until the queue fully drains.
- `file_storage` refuses a `max_size` below its 100 MiB compaction threshold,
  which the profiles do not expose.

### Finding 06: durable admission is not eventual delivery

The liveness property is:

> Admitted(e) ∧ recipients eventually available ∧ sufficient capacity ∧ no
> permanent delivery error ⇒ eventually delivered(e).

It depends on how the recipient's answers are classified, and the pinned
exporters classify broadly as permanent:

- HTTP 500 and every status other than 429, 502, 503 and 504 is permanent.
- gRPC `Internal`, `Unknown` and every other code outside the retryable set is
  permanent.

**One transient HTTP 500 drops an admitted record** (proven by test,
[PC-07](problem-cards/PC-07-permanent-error-after-admission.md)). A partial
success is counted as delivered, and its rejected records are dropped
(proven by test, [PC-08](problem-cards/PC-08-recipient-partial-success.md)).
Neither is a violation of durable admission, but both bound what "admitted"
promises.

### Finding 07: duplicate delivery

Delivery is at least once, not exactly once. Duplicates arise in five places
([PC-11](problem-cards/PC-11-at-least-once-duplicate-windows.md),
[PC-03](problem-cards/PC-03-gateway-trace-fan-out.md),
[PC-05](problem-cards/PC-05-blocked-admission-and-deadlines.md)):

- a recipient accepted the request, but the answer was lost before the item
  was deleted (proven by test);
- a fan-out branch persisted the request while another branch failed, and the
  producer retried (proven by test);
- a blocked request was persisted after its producer gave up;
- a meta-page sync failed after the meta page was written;
- after a restart, in-flight items are replayed at the back of the queue, with
  no ordering guarantee.

No end-to-end deduplication exists. Recipients must deduplicate by a
producer-supplied identity.

### Finding 08: what a Go telemetry producer can rely on

The collector parses only OTLP and never interprets producer payload schemas
(supported by inspected source: no component reads producer attributes except
the classification filter and redaction). Identifiers and correlation survive
(proven by test, [PC-10](problem-cards/PC-10-identity-and-correlation-preservation.md)):

- trace, span, parent span and link IDs;
- producer attributes outside the redaction key set.

The collector adds only generic attributes: `resource_detection` adds host and
OS attributes without overriding the producer's, and redaction adds
`redaction.masked.count` to a record it changed. It manufactures no
Langfuse-specific attribute.

A producer may rely on this:

1. A 200 or gRPC OK means every item in the request is in each required WAL on
   that host, durable against process crash. Durability against power loss
   holds only to the extent of the storage assumptions in Finding 04.
2. Any non-success means the request was not acknowledged. It may still be
   partly persisted, so a retry can duplicate it.
3. Delivery is at least once, unordered across restarts, and bounded by the
   recipients' answers (Finding 06).

A producer must do this:

- retry 503, 429, `Unavailable` and client timeouts with its own backoff;
- set a deadline;
- keep each request below the edge `queue_size` and its receiver limit;
- put a stable event identity in an attribute;
- keep identifiers and usage values out of blocked key segments
  (`token`, `auth`, `secret` and the others). For example, OpenInference
  `llm.token_count.*` arrives as `****`; use `gen_ai.usage.*` instead.

Open protocol questions, not answered by standard OTLP here:

- **Recipient rejections.** The producer has no channel through which
  recipient-side rejections (partial success, permanent errors after
  admission) flow back.
- **Delivery receipts.** A producer cannot learn that a record reached a
  recipient. Admission is the last acknowledgement it gets.

### Finding 09: answers to the assignment's decision questions

1. **Does the collector already provide the durable admission contract?**
   Yes for process crash, on both roles, every signal and both protocols, with
   the two narrow upstream hazards PC-13 and PC-14 not yet refuted. Eventual
   delivery is not provided under recipient 500, `Internal`, `Unknown` or
   partial success.
2. **Which assumptions remain unresolved?**
   - storage flush semantics under power loss;
   - power loss after a compaction rename;
   - PC-13's contended path;
   - PC-14's restart window;
   - recipient answers that the exporter classifies as permanent;
   - no free-disk or storage-size telemetry on macOS.
3. **Are code changes needed?** None for admission. The decision on recipient
   error classification is needed before eventual delivery can be claimed; the
   existing wrapper seam can carry it. The other gaps are telemetry and
   upstream fixes.
4. **What can the Go engine rely on?** The Finding 08 contract.
5. **Is a producer-side OTLP WAL redundant?**
   - **Process crash:** it is redundant for collector crashes once a request
     is acknowledged. The local edge already provides that boundary, at the
     cost of one loopback hop.
   - **Before acknowledgement:** it is still necessary for data the producer
     holds before an acknowledgement, including while the edge is down,
     refusing or blocked. This is the engine's source checkpointing, which the
     assignment already places with the engine.
   - **Stronger requirements:** it is also necessary where the producer needs
     guarantees beyond those listed, namely power-loss durability on hosts
     whose storage does not honour flushes, delivery confirmation, or recovery
     from a recipient's permanent rejection.
   - **Conclusion:** checkpointing the source until acknowledgement is
     sufficient. A second WAL of already-acknowledged OTLP is not.

### Proposal: recommendations ranked by necessity

1. **Decide the recipient error classification.** This is required for any
   eventual-delivery claim. Two options:
   - keep upstream behaviour and document it as a recipient obligation;
   - reclassify HTTP 500 and gRPC `Internal`/`Unknown` as retryable in the
     wrappers, with a bounded interval and alerting.

   The trade-offs are in
   [PC-07](problem-cards/PC-07-permanent-error-after-admission.md).
2. **Make early warning a safety requirement while PC-13 stands.** Alert on
   `queue_size / queue_capacity` well below 1, alert on missing telemetry from
   a node, and choose a macOS disk-space source. The options are in
   [PC-04](problem-cards/PC-04-capacity-early-warning.md).
3. **Report PC-13 and PC-14 upstream.** For PC-13, propose skipping a failed
   read without deleting the item. For PC-14, propose making restart
   re-enqueue a single transaction.
4. **Publish the producer contract** in Finding 08 in the reference
   documentation once the owner accepts it.
5. **Low priority hardening:**
   - add a storage fault-injection seam if PC-13 or PC-14 must be proven;
   - test compaction with a 100 MiB fixture if the CI budget allows.

## Sources And Limits

- **Code references:** upstream references are module paths in the Go module
  cache at the versions `builder.yaml` resolves. They are cited in the cards.
- **Tests:** the test names refer to `test/harness/`.
- **Local verification:** the local runs used Go 1.27.3 because govulncheck
  rejects the workflow's 1.27.2 pin (GO-2026-6809). That pin change is
  outside this audit.
- **Not exercised:** power loss, real ENOSPC and heap pressure. Their rows rest
  on source and on external contracts.
- **Host agent:** it was examined only for contrast and is outside the
  acknowledgement contract.
